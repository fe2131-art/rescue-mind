# v1.0 → v1.1：改善サイクルと優秀賞戦略

## 評価項目→示すべき証拠
|講座の加点要素|現在の工夫|最終動画・レポートで必要な実測|
|---|---|---|
|創造性|現地でJev・Qwenの二重判断を行い次の行動を決める|同じ走行条件で「一致→続行」と「不一致→停止」を映す|
|技術力|画像Header時刻の鮮度、LiDAR、Odometry、カメラheartbeat、停滞監視|実Gazeboの走行ログ・画像・モデル応答・動作指令のイベント順序|
|実用性|誤物資を避けるfail-closed判断|危険な誤許可率だけでなく誤拒否率、遅延、停止と復帰手順|
|表現力|画像、判断、実際の経路を一つの時系列に集約|1〜3分の動画で変化が視覚的に分かり、比較は実測値のみ|

### Audit 1: カメラ配信停止が検出できない
以前：ROS Headerの時刻単調性だけ検査。画像が止まったときには「逆行」とならず、最後の画像を依然として保持できる。
修正：`CameraWatch` を導入。異常時刻・逆行と**撮影時刻の長時間不更新**を区別し、ライブ走行・現地判定・API待ちに適用。LiDARが正常でもカメラが止まればミッション停止。
検証：単体テスト（健康/欠落/複写/逆行/時刻無効）、模擬ROSで実制御の停止試験、500件の人工故障キャンペーン。

### Audit 2: 実行証拠の上書きリスク
以前：`outputs/on_site_supply.jpg`や`outputs/gazebo_direct_run.json`が固定既定名。複数回の試験で内容を上書きし、誤った画像とログの対応付けが起こり得る。
修正：ランダム`run_id`を生成し、標準保存先を`outputs/runs/<run_id>/`とした。ログに撮影ファイル名・ハッシュ・ROS撮影時刻を記録し、証拠パッケージ側もv1.1のrun_idと画像名を照合。**明示した`--out`/`--checkpoint-image`は上書き回避の対象外**なので作業者が注意する。
検証：一意IDを持たないログや別名の画像を拒否するテスト。

### Audit 3: 観測の安全性の意味を誤認しない
物資棚に写った「危険なし」は、**通路全体が安全**という意味ではない。画像AIは物資の判断と可視範囲にある危険兆候に限定し、移動時のLiDARで近接を確認する。LiDARも障害物周辺の再経路探索機能ではない。

## 次のゲート（追加機能より優先）
1. Ubuntu 24.04 + ROS 2 Jazzy + Gazebo Harmonicでワールドの起動と`/odom` `/scan` `/camera` `/cmd_vel`確認。`--motion-check`の目標到達を実測。
2. 物資棚をロボットカメラが正しく撮影できることを画面で確認。JevとQwenの実API出力が記録できたら、初めてライブミッションを実行する。
3. 正解ラベルを固定した**未使用の実画像**でJev単独・Qwen単独・Jev＋Qwenをペア比較。誤許可、誤拒否、遅延の信頼区間を含める。
4. 成功と停止の両動画を撮り、OmniCampusに提出可能な120秒前後へ編集。映像はGazebo/ROSの**実際の操作**、カメラ画像・ログは生成された実ファイルを使用。
5. 2026年10月23日までに独自Gazeboで走らなければ、公式Nav2 TurtleBotの運転実証を優先して提出要件を確保。

## 誇張・虚偽表示の禁止
モックはAPI応答形式とロジックの検証に限定する。人工500件の成功率100%は**AI認識精度100%や実ロボット成功率100%を意味しない**。ロボットが実際に把持・配送した動画がない限り「配送完了」とは書かない。
