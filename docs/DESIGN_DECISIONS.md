# 設計判断の記録（ADR）

各判断は「背景 → 選択肢 → 決定 → 根拠（データ）→ 代償」で記す。数値は `experiments/results/` から再生成できる。

## D1. AIはローカル実行（クラウドAPIを使わない）
* **背景**：災害時は通信が途絶・輻輳しやすい。現場画像を外部へ送ることにも抵抗がある。
* **決定**：視覚・言語の推論はすべて単一GPU（Tesla V100 32GB）上で完結させる。VLMサーバは 127.0.0.1 のみで待ち受ける。
* **代償**：使えるモデルが VRAM と GPU 世代（V100 は BF16 非対応 → FP16）に制約される（D7）。

## D2. VLMに文章を書かせず「選択肢の確率」で判断する
* **背景**：引継ぎ版の自由生成JSONは、実画像で96応答中21件が解析不能、空の台で「水」と幻覚した。
* **決定**：選択式の質問を出し、次トークンの選択肢文字（A/B/C、Yes/No）の確率を1回の順伝播で読む。2問で**選択肢の順序を入れ替え**、両方で依頼物資が最大かつ 0.50 以上、危険 0.50 未満のときだけ許可。
* **根拠**：開発セット48枚で 37/48 → 48/48、解析不能 0（[`IMPROVEMENT_LOG`](IMPROVEMENT_LOG.md)、[`FINDINGS`](FINDINGS.md) #8）。
* **代償**：未知の物体は「その他」としか分からない → 人向けの説明は別経路（D5）。

## D3. 成功の証明は Gazebo の真値で行う（制御器のオドメトリを信用しない）
* **背景**：車輪軸の定義誤りで、オドメトリ上は前進していても実際の車体は進んでいなかった。オドメトリ基準の監査はこれを見逃す。
* **決定**：シミュレータのモデル真値を別トピックで記録し、到着・停止・転倒・オドメトリ乖離を監査する。制御器は真値を購読しない（現実のロボットに無い情報で走らない）。
* **根拠**：FINDINGS #1, #2、I-01（ドリフト 0.16 m → 0.011 m を真値で確認）。

## D4. 物資が違えば「1回だけ」別拠点を探す。危険なら探さない
* **背景**：止まるだけでは在庫情報のずれに対応できない。一方、探索は危険な場所を動き回るリスクがある。
* **決定**：「物資違い・欠品」かつ危険なしのときだけ、もう一方の拠点で同じ確認を1回行う。危険・確信度不足・2回目の拒否は停止して人に委ねる。
* **根拠**：I-02 実走（取り違え → 探索 → 配達、欠品 → 両拠点で拒否、火災 → 即停止）。

## D5. 人への説明文は判断に使わない
* **背景**：拒否理由が確率値だけでは現場の人が動けない。しかし自由記述は幻覚しうる。
* **決定**：判断が確定した**後**に、VLMで日本語1文の状況説明を生成し、ログ・画面に「報告」として出す。判断ロジックは説明文を読まない（コードとテストで保証）。
* **根拠**：I-03（モデルにより説明の正確さ 66〜98%）。

## D6. 開発データと評価データを分け、評価前に条件を固定する
* **決定**：プロンプト・閾値・モデル選択は開発セット（視覚：v1 48枚＋v2 128枚、指示文：dev 40文）だけで決め、評価（閉ループ試行、指示文 held-out 60文）の前に [`experiments/PREREGISTRATION_*.md`](../experiments/) に固定する。失敗・中断した評価も台帳から削除しない。
* **代償**：評価のやり直しには新しい事前登録が要る（評価A・Bの中断はすべて記録）。

## D7. モデル選定（I-08）
* **背景**：引継ぎ時点のモデル（Qwen2.5-VL-3B、2025年1月）は研究用途ライセンス。より新しい世代（Qwen3-VL 2025年10月、Qwen3.5 2026年2月、いずれも Apache-2.0）がある。
* **制約**：V100 32GB・FP16。27B 以上は FP16 で収まらない。Qwen3.5 は線形 attention を含む新構造で、V100 向けの高速カーネルが無く PyTorch 参照実装で動く。
* **決定**：**Qwen3.5-9B**（2026-02、Apache-2.0、FP16で約18 GB）。
* **根拠**：同一データ・同一手順の比較で、視覚の誤許可0・指示の危険な誤受理0を両立した唯一の新世代モデル。説明文の正確さ 125/128（3Bは84）。指示理解テスト 55/60・危険0。詳細は [`IMPROVEMENT_LOG.md` の I-08](IMPROVEMENT_LOG.md)。
* **代償**：Qwen3-VL-8B より約2倍遅い（V100向け線形attentionカーネルが無いため参照実装）。旧スタック（Qwen2.5-VL-3B）も `STACK=v33` で再現可能なまま残す。


## D8. 速度要求が途絶えたとき：動作中なら停止、停止中なら待つ
* **背景**：4コアのホストでは稀にミッションの送信が0.3秒程度止まる。起動待機中にこれが起きると、ガードがミッション全体を中止していた（評価Dのインフラ失敗2件）。
* **決定**：最後の要求が速度0なら、途絶してもラッチせず0を出し続ける。動作中の要求の途絶は従来どおり即ラッチ（0.45秒）。
* **根拠**：停止中の0出力は危険を増やさない。停止注入の再現実験で旧 2/2 失敗 → 新 2/2 完了（I-09）。安全側の性質（動作中の途絶で必ず止まる）は単体テストで保証。


## D9. 小さな隠れた火は、閾値を下げずに問い方と切り出しで拾う
* **背景**：評価Fで、v3.5 は小さな火が見えていた13世界のうち 12 で配達した。見逃した火のp(危険)は約0.003で、火の無い画像の値と重なっていた（I-14）。
* **決定**：閾値をさらに下げる代わりに、危険の質問の**問い方（h36：小さい・隠れた・画面の端で切れた火や煙を明示）**と、**全体＋拡大切り出し3枚（左・右・上）の最大値**を使う。τ_h は 0.05 のまま（I-10）。
* **根拠**：見逃した火のp≈0.003は火の無い画像と重なるので、閾値では分離できない。開発データ（見える火211枚）では、v3.5 が止めた火 165 → h36＋切り出し 194、誤許可 46 → 17（I-11, I-13）。効いたのは主に問い方で、切り出しは問い方との組み合わせで効く。
* **代償**：モデル呼び出しが増える（危険の質問は画像ごとに1回だけ計算してキャッシュし、相殺）。それでも評価Fでは構成Bが 7/13 を見逃した（I-14）。

## D10. 大きなモデルに替えず、横から見る（能動知覚）
* **背景**：D9 で残った見逃しは、物資の陰で火が正面からほとんど写らないことが原因。モデルを大きくしても写っていないものは見えない。
* **決定**：許可の前に、ステーションの左右0.4 mへ移動して危険だけを再判定する（`--look-around 0.4`）。どちらかで危険なら拒否し、探索はしない。採用は評価Gで判断する。
* **根拠**：マスク画像だけでの設計確認で、同じ火の多くは正面から1,100〜2,400画素（7件中6件。残る1件は8,573画素）、左右0.4 mからは4,600〜22,000画素（例：W11 は 1.3k → 9.7k）。開発用の予備走行では、Bが見逃した世界を含む火のある5世界すべてを横からの画像で停止した（I-14）。
* **代償**：配達1回あたり約+30秒。横からの物資判定は使えない（物資が見えないことがある）ので危険だけを見る。

## D11. 「Jev の役割」はローカルの判断モデルで、正直な書き方で
* **背景**：当初計画の中心は「異なる2つのAIで次の行動を決める」ことだったが、1モデルへ縮退していた（I-13）。Cloudflare の Clef-Flash は Jev/SystemOne 互換でローカルに動く。
* **決定**：`scripts/clef_server.py` で Clef-Flash をローカル配信し、Qwen と**両方が許可したときだけ許可**する（任意）。V100 1台には載らない（Qwen3.5-9B と同時に約37 GB）ので、**評価した構成であって既定ではない**と明記する。
* **根拠**：当初の Jev 要求は「通路」の安全を問うため物資の存在確率が低く出て、正しい配達の半分を拒否した（開発データ 182/360）。課題に合わせた質問にすると 350/360。つまり判断モデルの成否は質問の書き方に強く依存するので、公平のため両方の結果を報告する。課題向けの質問を使った Clef-Flash 単独は T2 で v3.5 と同等だった。
* **代償**：2モデルの合議は誤許可が最少（開発データ 15/413）だが、正しい許可が下がり（357 → 350）、オンボードでは使えない。
* **系統の注意**：Clef-Flash は Qwen/Qwen3.5-9B からの追加学習（モデルカード：`base_model_relation: finetune`）なので、2モデルは独立ではない。多様性は追加学習・大きさ・質問の書き方に由来し、相関した失敗は残り得る（Knight & Leveson, 1986）。「独立した2つのAI」とは書かない。

## D12. 開発セットには、狙う失敗が入っていなければならない
* **背景**：DH（30世界・300枚）は見える火99枚のうち1万画素未満が**4枚**しかなく、狙う弱点（物資の陰の小さな火）を見分けられなかった。途中結果の v3.5 でも 97/99で、候補間の差は1〜2枚＝ノイズ。
* **決定**：選定規則は変えずに、小さな初期火災を中心とした DH2（300枚）を**選定の前に**追加し、DH＋DH2 に規則を適用する。DH の途中結果を見たうえでの追加であることを記録に明記した（I-13、T2 の Amendment 1）。
* **根拠**：判定する前に、開発セットが弱点を区別できるかを確認する。区別できないセットで選ぶと、選定が偶然に左右される。最終判断は未使用の T2 で行う。
* **代償**：結果を見たあとの追加なので、完全に事前の設計ではない。DH2 でも全候補が誤許可0にならず、規則1が何も選ばなかったため、救済規則（誤許可が最少で正しい許可 ≥95%）を採点前に追記した。

## D13. 記憶は「提案」だけ、判断はその場の知覚で（安全側への単調性）
* **背景**：同じ避難所へ何度も補給するなら、前回見たものを覚えておけば速くなる。ただし災害現場は出動のたびに変わり、古い記憶で動くのは危険（"When Memory Lies", Sun & Zhang 2026）。既存の記憶研究（ReMEmbR、Embodied-RAG、3Dシーングラフなど）は、記憶を検索や質問応答に使っており、「どこを・どれだけ確認するか」を記憶で決める際の安全規則は扱っていない。
* **決定**（I-15）：記憶にできるのは2つだけで、確認を減らすことは決してしない。
  * 順序の提案：前回物資が入れ替わっていたら、その物資を見た拠点へ先に行く。行った先でも必ず確認する。
  * 慎重さの追加：最近火を見た拠点では、すべての視点で危険の閾値を 0.05 から 0.01 に下げ、火が見えた側から先に見る。
* **根拠**：判定式は τ_h を下げるほど許可が減り、横からの見直しは「すべての視点で安全」の AND になっている。したがって同じ画像なら、記憶を使った許可は記憶なしの許可の部分集合になる（安全側への単調性）。この性質はコードで強制し（`apply_memory_caution`・`peek_hazard`）、監査は保存された出力から記憶による判定を再計算する。
* **代償**：記憶が古い（元の配置に戻った）場合は、1拠点ぶん遠回りになる。比較対象として、記憶を信じて確認を省略する素朴な記憶（M1）も実装した。M1 は評価Hで測るためだけに使い、既定にはしない。

## D14. Jev役は課題向けの質問で、V100 1台に載る組（Clef-Flash＋Qwen3.5-4B）で実機評価する
* **背景**：D11 の構成（Clef-Flash＋Qwen3.5-9B）は約37 GB で V100 1台に載らず、オフライン評価止まりだった。実機の経路は当初の Jev 要求を固定で使い、正しい配達の約半分を拒否する状態だった（I-16）。
* **決定**：Jev役には課題向けの質問（`--jev-schema task`）を使い、Qwen は 3.5-4B に替えた組（Clef-Flash 19 GB＋Qwen 9 GB）で実機の閉ループ評価Jを行う。両方が許可したときだけ許可する点は D11 のまま。既定にはしない。
* **根拠**：T2 で `J2(Clef-task,0.05)+Q4B` は誤許可 0/407、正しい許可 185/193（`experiments/results/t2_summary.json`）。V100 1台に載る2モデル構成として評価済みなのはこの組だけ。
* **代償**：Qwen が小さくなる、GPU メモリが約28 GB 必要、確認が遅くなる。2モデルは系統を共有するので（D11）、独立性による安全の上乗せは主張しない。評価Jの結果で判断する。
